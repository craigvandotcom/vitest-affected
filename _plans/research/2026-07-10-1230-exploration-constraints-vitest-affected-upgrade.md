# Exploration Constraints — extraDependencies + BCA wave

## Constraint 1: extraDependencies failures must fail CLOSED (full-suite), never silently drop an entry
**Type:** Safety
**File(s):** src/plugin.ts:1080-1089 (catch-all), src/plugin.ts:796-810 (fullSuiteTriggers pattern to mirror)
**Impact:** A bad glob, a typo'd watched path, or a test-selector glob matching zero test files must not be swallowed as "no edges added." The existing precedent (`fullSuiteTriggers`) treats match-time errors as an escape hatch that over-runs, never under-runs. `extraDependencies` should route glob-compile/match errors through the same top-level `try/catch` (`catch (err) { ... emitStats(..., 'full-suite', 'error', ...) }`) rather than a local try/catch that eats the error and returns zero edges — a locally-swallowed error would degrade an entire watched-path rule to a no-op with no signal.
**Evidence:** `catch (err) { console.warn(...); emitStats(statsCtx, 'full-suite', 'error', {...}); }` (plugin.ts:1080-1089) is the single funnel every unexpected failure already routes through; `fullSuiteTriggers` matching is unguarded and lets a thrown RegExp/glob error propagate up into that same catch-all rather than being locally caught.

## Constraint 2: watched/test paths must converge through `toCanonicalPath` at the SAME boundary as graph keys and changed-file paths
**Type:** Paths
**File(s):** src/graph/normalize.ts:39-52,118-124; src/plugin.ts:597,780-782,955-963
**Impact:** `extraDependencies` config keys (test path/glob) and values (watched path/glob) must be resolved relative to `rootDir` and passed through `toCanonicalPath` before being used as reverse-map keys/values — exactly like `options.changedFiles` (plugin.ts:780-782, `toCanonicalPath(path.isAbsolute(f) ? f : path.resolve(rootDir, f))`) and glob'd test files (plugin.ts:955-963, `.map((f) => toCanonicalPath(f))`). Skipping this makes the injected edges compare unequal to git-derived changed-file paths or BFS test-file-set membership on macOS (`/var`→`/private/var`) or a symlinked rootDir, silently orphaning the edge (same failure class normalize.ts documents as "this plugin's most recurrent silent-failure source").
**Evidence:** normalize.ts:43-51 — "two representations of the same file compare unequal as Map keys, so a changed file silently fails to match its graph entry and gets dropped rather than erroring." plugin.ts:590-597 canonicalizes rootDir itself for this exact reason.

## Constraint 3: injected reverse edges must be written into the SAME `reverse` Map that mergeRuntimeEdges/cache own, and persisted through the v3 rootDir-relative boundary
**Type:** Paths / Contract
**File(s):** src/graph/cache.ts:357-393 (saveCacheSync), src/graph/types.ts, src/plugin.ts:682-708
**Impact:** Per the synthesis doc's architecture invariant, only durable reverse edges (not BFS seeds) survive a selective run — static parsing is seed-only. `extraDependencies` edges must be merged into `reverse: ReverseMap` (absolute canonical keys) BEFORE `saveCacheSync` runs, so `toRootRelative` (cache.ts:142-146) persists them in v3 format and `toConfinedReverseMap`'s `isUnderRootDir` confinement (cache.ts:56-60, 96) doesn't drop a watched path that resolves outside rootDir.
**Evidence:** cache.ts:186-206 documents v3's `reverseMap: Record<string, string[]>` is "source → test_files, rootDir-relative" — any edge not funneled through this save path is lost on the next cache load.

## Constraint 4: DEFAULT_RELEVANT_EXTENSIONS drops non-code watched-path extensions unless graphMembership or a config-basename/full-suite-trigger override fires
**Type:** Filtering
**File(s):** src/changed-files.ts:4-8,121-161
**Impact:** Watched paths like `.css`, `.sh`, `.yml`, `.mdx`, `.swift`, or extension-less dirs will be dropped by `isRelevant()`'s extension allowlist (`.ts/.tsx/.js/.jsx/.mts/.cts/.mjs/.cjs/.json` only) UNLESS they're already a key in the loaded `reverse` graph (`graphMembership` override, changed-files.ts:152-158) — which a freshly-configured `extraDependencies` entry is NOT until after its first save. `extraDependencies` must therefore either (a) pre-seed `reverse` with its watched-path keys before `filterRelevantChangedFiles` runs each session (so graphMembership always covers them), or (b) bypass the relevance filter entirely for extraDependencies-derived comparisons the way `fullSuiteTriggers` does (checked on raw `changed`/`deleted` before filtering, plugin.ts:791-810).
**Evidence:** changed-files.ts:145-150 extension allowlist; changed-files.ts:55-69 doc comment: "graph membership overrides the extension allowlist... Does NOT override an explicit ignoreChangedFiles rule or a built-in path/basename ignore."

## Constraint 5: adding extraDependencies as a selection input requires touching the stats/explain provenance contract, not just the BFS graph
**Type:** Contract
**File(s):** src/plugin.ts:106-117 (`explain` field doc), src/selector.ts:11-14 (SelectionTrail), test/shadow.test.ts:223-259 (every-exit contract)
**Impact:** The BFS itself needs no code change if extraDependencies is materialized as ordinary reverse-map edges (selector.ts is graph-shape-agnostic). But `SelectionTrail.chain` will now legitimately contain a non-import hop (watched path → test), and `explain-core.ts`'s CLI/`explainSelection` reason strings assume import-graph semantics ("why would test X be selected" reads as import provenance) — the "reason" text should be updated to not misrepresent an extraDependencies-sourced chain as an import edge. Every `configureVitest` exit must still emit exactly one DECISION line (shadow.test.ts:224-225 "every early return + catch-all writes exactly one line") — a new early-return for extraDependencies validation errors must follow the same `emitStats(...)` pattern as every other guard.
**Evidence:** plugin.ts:107-117 documents `explain: { [testPath]: { seed, chain } }` as import-chain provenance; shadow.test.ts:228 `describe('every-exit emission contract', ...)`.

## Constraint 6: config shape must stay JSON-serializable-adjacent and RegExp-compatible with existing `Array<string | RegExp>` precedent, never `any`
**Type:** Types
**File(s):** src/plugin.ts:78,106 (`ignoreChangedFiles`/`fullSuiteTriggers` shape), tsconfig.json:10 (`strict: true`), AGENTS.md ("TypeScript strict — no `any` types")
**Impact:** The interview-decided shape (test path/glob → watched paths/globs) should reuse `Array<string | RegExp>` or plain glob strings (tinyglobby-compatible) matching the existing `ignoreChangedFiles`/`fullSuiteTriggers` precedent — RegExp values are fine in the in-memory `VitestAffectedOptions` type (never persisted to the JSON cache, which only stores plain string paths per `CacheDiskFormatV3.reverseMap: Record<string, string[]>`, cache.ts:205). If extraDependencies-derived edges are persisted to cache.json, only the RESOLVED string paths may cross that boundary — RegExp/glob patterns must be expanded to concrete paths before `saveCacheSync`.
**Evidence:** plugin.ts:78 `ignoreChangedFiles?: Array<string | RegExp>`; cache.ts:205 `reverseMap: Record<string, string[]>` — no RegExp-serialization path exists anywhere in cache.ts.

## Constraint 7: cross-repo ordering — BCA's CI builds vitest-affected from the OSS repo's HEAD, so an unknown option is a silent TS compile-time risk only if BCA's vitest.config.mts is typed against the OLD dist
**Type:** Cross-Repo
**File(s):** ../body-compass-app/.github/workflows/quality-gate.yml:80-102 ("Checkout vitest-affected (OSS sibling)" + "Build + link vitest-affected sibling dist")
**Impact:** CI always checks out and builds vitest-affected fresh from `craigvandotcom/vitest-affected`'s current default-branch HEAD (`actions/checkout` with no `ref:` pin, quality-gate.yml:80-85) before symlinking `dist/` into the sibling location — so BCA's PR runs ALWAYS get the latest merged vitest-affected, never a pinned old version. This forces ordering: **the `extraDependencies` plugin feature must merge to vitest-affected main BEFORE BCA's config PR that references `extraDependencies` in `vitest.config.mts`** — otherwise BCA's own build step (`pnpm build` / `pnpm type-check`, quality-gate.yml:153-159) fails on an unknown property (TS excess-property check against `VitestAffectedOptions`) at BCA's own CI, not silently. Reverse ordering (BCA merges first) fails loudly, not silently — TS strict typing makes an unrecognized option a compile error, so no data-loss risk, only a sequencing/CI-red risk.
**Evidence:** quality-gate.yml:68-79 comment: "vitest.config.mts resolves the plugin from `../vitest-affected/dist/index.js`... and SILENTLY no-ops if it's absent" (the no-op risk is dist-ABSENCE, not version skew) + quality-gate.yml:80-85 unpinned checkout of `craigvandotcom/vitest-affected` confirms HEAD-always semantics.
